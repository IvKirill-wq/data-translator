# Структура проекта data-translator

Документ объясняет, что программа делает, из каких файлов состоит, почему
устроена так и в каком порядке её читать. Разделы идут от общей идеи к
конкретным файлам; в коде комментариев нет сознательно — всё объяснение здесь.

---

## 1. Что программа делает

Один прогон — три нажатия кнопки:

1. Вы вводите реквизиты базы-источника и **произвольный запрос** (`SELECT`,
   вызов функции, скрипт с временными таблицами — что угодно, что возвращает
   строки). Программа выполняет его и показывает список колонок результата.
2. Вы отмечаете **одну или сколько угодно колонок** с русскими значениями —
   или ставите галочку «Определить автоматически», и программа выбирает их
   сама, — и нажимаете «Выполнить перевод». Программа собирает уникальные
   значения этих колонок, переводит их ru→en и показывает таблицу
   «значение → перевод», по вкладке на каждую колонку.
3. Вы правите переводы руками и нажимаете «Применить». Программа **заново
   выполняет ваш запрос** и записывает его результат в целевую таблицу —
   все колонки, все строки, в том же порядке, — заменив значения переведённых
   колонок на утверждённые вами английские.

То есть на выходе не словарь из двух колонок, а **английская копия результата
запроса с полностью сохранённой структурой русского исходника**. Значения, для
которых перевода нет, остаются как были.

```
исходник (PostgreSQL / ClickHouse)        результат (PostgreSQL / ClickHouse)
┌──────┬───────────────┬───────────┐      ┌──────┬───────────────┬───────────┐
│ id   │ kind          │ note      │      │ id   │ kind          │ note      │
├──────┼───────────────┼───────────┤  →   ├──────┼───────────────┼───────────┤
│ 1    │ Договор       │ Отгрузка  │      │ 1    │ Contract      │ Shipment  │
│ 2    │ договор       │ NULL      │      │ 2    │ Contract      │ NULL      │
│ 3    │ Акт           │ оплата    │      │ 3    │ Act           │ Payment   │
│ 4    │ ATOL-15       │ Отгрузка  │      │ 4    │ ATOL-15       │ Shipment  │
└──────┴───────────────┴───────────┘      └──────┴───────────────┴───────────┘
         ↑ отмеченные колонки                      ↑ стали text/String
```

Колонок можно отметить сколько нужно: одинаковое значение в двух колонках
переводится один раз и одинаково (в движок уходит один запрос), а показывается
на двух вкладках.

Переводит не сама программа: она ходит в локальный LibreTranslate. Своя работа
программы — решить, что отправлять, что не отправлять, что защитить от перевода
и что запомнить на следующий раз. Именно в этом смысл слоя `core`: на реальных
данных в движок уходит меньшая часть значений.

## 2. Три слоя и одно правило

```
┌──────────────────────────────────────────────┐
│  routes + forms + templates + static         │  Flask: HTML, одна форма,
│  «что видит пользователь»                    │  четыре кнопки
└───────────────┬──────────────────────────────┘
                │ вызывает
┌───────────────▼──────────────────────────────┐
│  core                                        │  сценарий перевода: фильтр,
│  «бизнес-логика, ничего не знает о Flask»    │  защита, глоссарий,
│                                              │  клиент движка, пайплайн
└───────────────┬──────────────────────────────┘
                │ вызывает через протокол
┌───────────────▼──────────────────────────────┐
│  db                                          │  два адаптера: PostgreSQL,
│  «как выполнить запрос и как записать»       │  ClickHouse
└──────────────────────────────────────────────┘
```

Правило одно: **зависимости идут только вниз**. `core` не импортирует Flask и
не пишет SQL. `db` не знает, что его данные кому-то переводят. Проверяется это
элементарно: `python3 -m unittest discover -s tests -t .` проходит на машине,
где не установлено ни Flask, ни драйверов БД (раздел 13).

Четвёртого слоя — фоновых заданий — нет, см. раздел 11.

## 4. Точка входа, фабрика, конфиг

### `translator.py`

```python
from app import create_app

app = create_app()
```

### `app/__init__.py`

```python
def create_app(config_class=None):
    from flask import Flask

    if config_class is None:
        from .config import Config

        config_class = Config

    app = Flask(__name__, instance_relative_config=False)
    app.config.from_object(config_class)

    from .routes import bp

    app.register_blueprint(bp)

    return app
```

**Зачем фабрика.** Функция, создающая приложение, позволяет создать его дважды
с разными настройками (тесты) и убирает циркулярный импорт, неизбежный при
глобальном `app = Flask(__name__)`.

**Зачем импорты внутри функции, а не сверху.** Из-за них `import app.core...`
и `import app.db...` не требуют ни Flask, ни `SECRET_KEY` в окружении. По той
же причине `config.py` импортируется только когда свой класс настроек не
передали: иначе тест, который передаёт собственный конфиг, всё равно требовал бы
переменные окружения — класс `Config` читает их в теле класса, то есть на
импорте модуля. Это не
украшение: на этом держится и `scripts/bench_translate.py`, и тесты, и возможность отладить слой `core` там, где поднимать
веб-приложение негде. Если вынести `from flask import Flask` на уровень
модуля, всё это сломается, потому что `app/__init__.py` исполняется при любом
импорте внутри пакета.

### `app/config.py`

```python
BASE_DIR = Path(__file__).resolve().parent.parent


class Config:
    SECRET_KEY = os.environ['SECRET_KEY']

    LIBRE_TRANSLATE_URL = os.environ['LIBRE_TRANSLATE_URL']
    LIBRE_TRANSLATE_KEY = os.environ.get('LIBRE_TRANSLATE_KEY', '')
    TRANSLATION_BATCH = int(os.environ.get('TRANSLATION_BATCH', '24'))
    TRANSLATION_CHARS = int(os.environ.get('TRANSLATION_CHARS', '1200'))
    TRANSLATION_TIMEOUT = int(os.environ.get('TRANSLATION_TIMEOUT', '120'))

    MAX_RU_DISTINCT_QTY = int(os.environ.get('MAX_RU_DISTINCT_QTY', '5000'))
    INSERT_BATCH = int(os.environ.get('INSERT_BATCH', '10000'))

    GLOSSARY_PATH = os.environ.get('GLOSSARY_PATH') or str(BASE_DIR / 'glossary.ini')
```

| переменная | смысл |
|---|---|
| `SECRET_KEY` | обязательна; подпись CSRF-токена формы |
| `LIBRE_TRANSLATE_URL` | обязательна; например `http://127.0.0.1:5000` |
| `LIBRE_TRANSLATE_KEY` | ключ, если ваш инстанс его требует |
| `TRANSLATION_BATCH` | максимум строк в одном запросе к движку |
| `TRANSLATION_CHARS` | максимум символов в одном запросе к движку |
| `TRANSLATION_TIMEOUT` | таймаут одного запроса к движку, секунды |
| `MAX_RU_DISTINCT_QTY` | предел уникальных значений за прогон, суммарно по всем колонкам |
| `INSERT_BATCH` | размер пачки при вставке в ClickHouse |
| `CLICKHOUSE_SAFE_TYPES` | `1` (по умолчанию) — обходить типы, на которых зависает конструктор дашбордов (даты и широкий `Decimal`); `0` — родные типы ClickHouse |
| `GLOSSARY_PATH` | файл глоссария (`glossary.ini`) |

Две обязательные переменные читаются через `os.environ[...]`, а не
`os.getenv(...)`. Разница принципиальная: `getenv` вернёт `None`, приложение
поднимется, и вы узнаете о проблеме через час — `SECRET_KEY = None` молча
отключает защиту форм. `os.environ[...]` падает сразу и с именем переменной в
тексте ошибки. У числовых параметров значение по умолчанию обязательно
**внутри** `get`: `int(os.getenv('TRANSLATION_BATCH'))` при отсутствующей
переменной даёт `TypeError` на импорте.

**`MAX_RU_DISTINCT_QTY` по умолчанию 5000, а не 50000.** Это не только предел
нагрузки на движок: третий блок — это столько же полей ввода на одной
странице. Пять тысяч браузер рисует, пятьдесят — уже нет. Если значений
действительно больше, сужайте запрос, а не поднимайте предел.

Портов в конфиге нет: их вводит пользователь в форме. Разные контуры живут на
разных портах, и дефолт в конфиге означал бы правку файла на сервере вместо
поля на экране.

## 5. Реквизиты подключения: почему их негде хранить

**Реквизиты не хранятся на сервере вообще.** Пользователь вводит СУБД, хост,
порт, пользователя, пароль и базу в форму, и они приходят в теле каждого
POST-запроса. Повторно печатать их не надо — страница перерисовывается со всеми
заполненными полями, то есть значения держит браузер, а не сервер.

Это сознательный отказ от реестра подключений с `conn_id` и TTL. Такой реестр
нужен ровно в одном случае: когда фоновое задание продолжает работать после
того, как HTTP-запрос закончился, и ему нужны живые реквизиты. Фоновых заданий
здесь нет (раздел 11), поэтому реестр был бы слоем, который ничего не решает.

Из отказа следуют три вещи, и каждую надо знать.

**Первое. Форма обязана быть POST, а не GET.** Строка запроса GET попадает в
лог nginx, в лог werkzeug, в историю браузера, в заголовок `Referer` и в логи
любого прокси по дороге. Пароль в query string — это пароль открытым текстом в
пяти местах.

**Второе. Пароль попадает в HTML ответа.** Чтобы на втором и третьем шаге не
заставлять человека вводить реквизиты заново, поле пароля перерисовывается со
значением:

```python
src_password = PasswordField(
    'Пароль', validators=[Optional()], widget=PasswordInput(hide_value=False)
)
```

По умолчанию `PasswordField` значение обратно не подставляет, и в обычном
приложении отключать это не следует. Здесь это цена отказа от серверного
хранения: пароль виден в исходном коде страницы и живёт в DOM до перехода на
другую страницу. Поэтому страница отдаётся с `Cache-Control: no-store`.

**Третье. Поднимите HTTPS**, если приложение доступно не только с localhost.
POST прячет пароль от логов, но не от того, кто слушает сеть.

## 6. Слой `db`: протокол и два адаптера

Это самая важная часть документа, потому что именно здесь чаще всего делают
ошибку — пишут «универсальный класс для работы с БД».

### 6.1. Почему не один класс на обе СУБД

ClickHouse и PostgreSQL устроены принципиально по-разному:

| | ClickHouse | PostgreSQL |
|---|---|---|
| протокол | HTTP, блоками колонок | своё соединение, построчно |
| библиотека | `clickhouse-connect` | `psycopg` (версия 3) |
| экранирование имён | обратные кавычки `` ` `` | `psycopg.sql.Identifier` |
| описание результата | `column_names` / `column_types` | `cursor.description` + OID |
| потоковое чтение | блоки по сети | именованный курсор на сервере |
| вставка пачкой | `client.insert` | `COPY ... FROM STDIN` |
| DDL таблицы | нужен `ENGINE` и `ORDER BY` | обычный `CREATE TABLE` |
| NULL | только через `Nullable(T)` | у любой колонки |

Единый класс, который делает вид, что это одно и то же, будет состоять из
`if self.kind == 'clickhouse'` и превратится в кашу. Правильный подход: узкий
общий **протокол** и две независимые реализации.

### 6.2. `app/db/base.py` — протокол и типы

```python
@dataclass(frozen=True)
class ConnParams:
    engine: str
    host: str
    port: int
    user: str
    password: str
    database: str


@dataclass(frozen=True)
class Column:
    name: str          # имя как его отдала СУБД
    kind: str          # логический тип: text, int, bigint, ubigint, decimal, ...
    raw_type: str      # родной тип: 'int4', 'LowCardinality(String)', ...
    precision: int = 0 # для decimal: всего знаков
    scale: int = 0     # для decimal: знаков после запятой

    @property
    def is_text(self) -> bool: ...
    def as_text(self) -> 'Column': ...
    def renamed(self, name) -> 'Column': ...


class RowStream(Protocol):
    columns: Sequence[Column]
    def __iter__(self) -> Iterator[tuple]: ...


class DbAdapter(Protocol):
    def columns(self, sql_text) -> list[Column]: ...
    def rows(self, sql_text): ...                     # контекстный менеджер → RowStream
    def fit_columns(self, columns) -> list[Column]: ...
    def table_columns(self, table) -> list[Column] | None: ...
    def create_table(self, table, columns) -> None: ...
    def insert(self, table, columns, rows, batch=10_000, clear=False) -> int: ...
```

Пять решений, которые стоит заметить.

**Методов `list_tables` и `list_columns` нет.** Источник данных — не таблица, а
произвольный запрос: сплошь и рядом данные отдаёт хранимая процедура или
функция, и перечислять таблицы в такой схеме бессмысленно. Колонки берутся из
описания результата уже выполненного запроса.

**Чтение — это контекстный менеджер, а не метод, возвращающий список.**
`rows()` отдаёт объект с полем `columns` и итератором по строкам, живущий
внутри `with`. Иначе невозможно отдать наружу поток строк, не материализовав
его: соединение и курсор нужно закрыть после того, как потребитель всё прочёл,
а не до.

```python
with adapter.rows(sql_text) as stream:
    index = column_index(stream.columns, column)
    for row in stream:
        ...
```

**Гранулярность протокола — «операции над данными без знания, зачем они
нужны».** Слишком низкий уровень (`execute(sql)`) плох: SQL начнёт писаться в
`core`, и диалектные различия протекут в бизнес-логику. Слишком высокий
(`translate_query(...)`) тоже плох: вся логика уедет внутрь адаптера и
продублируется дважды.

**Очистки таблицы в протоколе нет — есть `insert(..., clear=True)`.** Отдельный
метод «очисти таблицу» выглядел бы честнее, но он означал бы отдельную
транзакцию: сначала коммит `TRUNCATE`, потом запись. Любая ошибка между ними —
и вместо прошлых данных пусто, а новых нет. Поэтому очистка выполняется внутри
той же транзакции, что и запись: в PostgreSQL это `TRUNCATE` и `COPY` на одном
соединении с одним коммитом, то есть либо таблица заменена целиком, либо не
тронута. ClickHouse транзакций не знает, и там это по-прежнему два шага — но
протокол одинаковый, а поведение описано в 7.5.

**`fit_columns` — право приёмника поправить имена колонок под свои правила.**
PostgreSQL обрезает любой идентификатор до 63 **байт** (кириллица — два байта
на символ), и без этого шага перенос из ClickHouse с длинными именами колонок
работал бы один раз: при повторном прогоне имена из запроса (полные) не
совпали бы с именами в таблице (обрезанными), и программа навсегда отказывалась
бы писать. Адаптер PostgreSQL обрезает имена так же, как сервер, и сразу
проверяет, что обрезанные имена не стали одинаковыми; ClickHouse возвращает
список как есть.

Ошибки обоих адаптеров — это `DbError` с текстом, который можно показать
человеку. `split_table('схема.таблица')` разбирает имя на две части (имя с
точкой внутри не поддерживается — это сознательное упрощение).

Ещё одна общая проверка живёт в `base.py` и вызывается из `describe` обоих
адаптеров: **повторяющиеся имена колонок отвергаются сразу**, на первой кнопке.
`SELECT * FROM orders o JOIN clients c ON ...` отдаёт две колонки `id`, и
`CREATE TABLE` с двумя `id` не создать. Без проверки это выяснилось бы только
на «Применить» — после того, как человек вручную выправил сотню переводов.

### 6.3. Выполнение произвольного запроса: три решения

**Первое. Режима «только чтение» нет — ни в одной из СУБД.** В прежней
редакции документа PostgreSQL получал `conn.read_only = True`, а ClickHouse —
`readonly = 2`. Убрано по требованию: данные нередко отдаёт хранимая
процедура, а она внутри себя создаёт временные таблицы, пишет в служебные и
делает ещё что угодно. В режиме только чтения такой источник просто не
работает. Следствие принимаем прямо: **программа выполняет то, что вы
написали, с правами того, чьи реквизиты вы ввели.** Опечатка вида `UPDATE`
вместо `SELECT` выполнится. Защита здесь одна и она не в коде: давайте
приложению реквизиты пользователя, которому в этой базе разрешено ровно то,
что нужно.

**Второе. Ограничения «один оператор за раз» тоже нет.** Оно противоречило бы
первому: скрипт вида `CREATE TEMP TABLE ...; SELECT ...` — законный источник.
PostgreSQL-адаптер это прямо поддерживает: после `execute` он прокручивает
результаты через `cursor.nextset()`, пока не найдёт первый, у которого есть
`description`, то есть первый, вернувший строки.

**Третье. Запрос пользователя никогда не оборачивается в подзапрос.** Прежняя
редакция собирала уникальные значения так:

```sql
SELECT DISTINCT <колонка> FROM ( <запрос пользователя> ) AS src
```

Это удобно, но работает только если запрос можно поставить в подзапрос. Вызов
процедуры, скрипт из нескольких операторов, `CALL` — нельзя. Поэтому выбран
единственный путь, работающий всегда: **запрос выполняется как есть, строки
читаются потоком, уникальные значения считаются в Python.** Отсюда и
`MAX_RU_DISTINCT_QTY`: у этого пути нет защиты со стороны СУБД, и предел нужен
в самой программе.

Цена решения: запрос выполняется дважды — один раз на «Выполнить перевод», ещё
раз на «Применить». Для `SELECT` это просто лишнее чтение. Если ваш источник
имеет побочные эффекты, он их произведёт дважды — знайте это заранее. Если
между двумя прогонами в данных появились новые значения, перевода для них нет,
и они останутся на русском (раздел 7.5).

### 6.4. `app/db/types.py` — соответствие типов

Чтобы создать целевую таблицу, нужно перевести тип колонки источника в тип
целевой СУБД. Делается это через узкий набор **логических типов** — ровно
столько, сколько можно отобразить в обе стороны без вранья:

| логический | PostgreSQL | ClickHouse (по умолчанию) | ClickHouse (`CLICKHOUSE_SAFE_TYPES=0`) |
|---|---|---|---|
| `text` | `text` | `String` | `String` |
| `int` | `integer` | `Int32` | `Int32` |
| `bigint` | `bigint` | `Int64` | `Int64` |
| `ubigint` | `numeric(20, 0)` | `UInt64` | `UInt64` |
| `float` | `double precision` | `Float64` | `Float64` |
| `decimal` | `numeric` | **`Decimal(p, s)`, `p + s ≤ 28`** | `Decimal(38, 9)` |
| `bool` | `boolean` | `Bool` | `Bool` |
| `date` | `date` | **`Date`** | `Date32` |
| `datetime` | `timestamp` | **`DateTime`** | `DateTime64(3, 'UTC')` |
| `datetimetz` | `timestamptz` | **`DateTime('UTC')`** | `DateTime64(3, 'UTC')` |
| `uuid` | `uuid` | `UUID` | `UUID` |

Колонки ClickHouse всегда создаются `Nullable(...)`.

Правила распознавания простые и намеренно грубые:

- PostgreSQL: имя типа берётся по OID из реестра `psycopg.postgres.types`
  (`int4`, `timestamptz`, `numeric`, ...), всё неизвестное — `text`. Массивы,
  `interval`, `json`, `jsonb`, `bytea`, `money` сюда и попадают.
- ClickHouse: с типа снимаются обёртки `Nullable`, `LowCardinality`,
  `SimpleAggregateFunction`, дальше сравнение по имени; `Decimal*` →
  `decimal`, `DateTime*` → `datetime` (или `datetimetz`, если в типе указан
  часовой пояс), `Enum`, `Array`, `Map`, `Tuple`, `IPv4` и прочее — `text`.

Про беззнаковые целые ClickHouse стоит сказать отдельно, потому что здесь легко
получить аварию на вставке: `UInt32` не влезает в `integer` PostgreSQL, а
`UInt64` — в `bigint`. Поэтому `UInt32 → bigint`, а `UInt64` получил свой
логический тип `ubigint` с отображением в `numeric(20, 0)`: это ровно те
значения, которые у вас встречаются чаще всего (`cityHash64`, идентификаторы).
`Int128`, `Int256`, `UInt128`, `UInt256` отправлены в `text` сознательно —
молча потерять старший разряд хуже, чем получить строку.

Всё, что стало `text`, при записи приводится к строке функцией
`pipeline.as_text` (раздел 7.5): строка остаётся как есть, словарь и список
становятся JSON (`["а", "б"]`, а не питоновский `['а', 'б']` — так результат
можно разобрать в ClickHouse через `JSONExtract`), `bytes` — шестнадцатеричной
строкой, всё прочее — `str(value)`. Это честный компромисс: массив из
ClickHouse в PostgreSQL попадёт текстом, а не как `text[]`. Зато таблица
создаётся и данные не теряются. Два места, где компромисс заметен:

- `numeric` **без объявленной точности** в PostgreSQL → `Decimal(38, 9)` в
  ClickHouse: это единственный случай, где знаки после девятого теряются.
  Когда точность объявлена (`numeric(20, 12)`, `Decimal(18, 4)`), она
  переносится в целевую таблицу один в один — именно для этого `Column` несёт
  `precision` и `scale`. PostgreSQL отдаёт их в описании курсора, ClickHouse —
  в имени типа.
- колонки `Enum8`/`Enum16` ClickHouse в целевой таблице становятся `String`.
  Прежняя редакция документа запрещала их переводить, потому что значение
  перечисления — часть определения типа; теперь запрет не нужен: целевая
  колонка не перечисление.

#### Почему даты и `Decimal` ограничены

Конструктор запросов в системе дашбордов **зависает**, если в базе есть хотя бы одна
таблица или представление с типом, которому его драйвер не находит соответствия.
Зависает не на этой таблице, а на всей базе: достаточно одного `Date32` в соседнем
объекте. Проблема всплыла именно на переведённых таблицах, потому что прежняя карта
создавала `Date32`, `DateTime64` и `Decimal(38, 9)` — то есть ломала базу, в которую
писала.

Подозреваемых удалось сузить, сравнив прежний вывод переводчика с картой приведений из
рабочего ETL-скрипта (он пишет в те же базы, и дашборды с его таблицами работают): там
есть `Int16`, `Int32`, `Int64`, `UInt32`, `Float32`, `Date`, `UUID`, `DateTime('UTC')` —
и нет ни `Date32`, ни `DateTime64`, ни `Decimal`. Значит целые, `UUID`, `Bool` и
`Float64` не при чём, а трогать надо ровно две группы:

- **даты** — вместо `Date32` пишем `Date`, вместо `DateTime64(3)` — `DateTime`
  (для типа с часовым поясом — `DateTime('UTC')`);
- **`Decimal`** — бюджет `p + s ≤ 28` разрядов.

Число 28 почти наверняка не про ClickHouse, а про `System.Decimal` в .NET: он держит
28–29 значащих разрядов. Это складывается в теорию, которая объясняет и остальное:
драйвер конструктора сопоставляет типы ClickHouse с типами .NET по фиксированной
таблице, и то, чему пары нет, уводит его в цикл — поэтому не исключение, а зависание.
Под эту теорию `Date32` и `DateTime64` не имеют пары (они новее), а `Decimal` шире 28
разрядов не влезает в `decimal`.

Цена двух ограничений:

- **`Decimal` обрезается под бюджет**, причём **дробная часть сохраняется**, а разряды
  отнимаются у целой: `Decimal(32, 4) → Decimal(24, 4)` (20 цифр до запятой — с запасом
  для любых сумм), `Decimal(38, 9) → Decimal(19, 9)`. Тихое округление копеек хуже, чем
  потеря заведомо лишних старших разрядов. Для `numeric` без объявленной точности
  берётся `Decimal(24, 4)`.
- **`Date` и `DateTime` начинаются с 1970 года** (`Date` — до 2149, `DateTime` — до
  2106), тогда как `Date32`/`DateTime64` держат 1900–2299. Значения вне диапазона
  записываются как `NULL`, и адаптер пишет в лог, сколько их было. Для даты рождения или
  «пустышки» `1900-01-01` это потеря: если такая колонка нужна как есть, приводите её к
  строке **в своём запросе** (`toString(дата)`), раз запрос приложение не переписывает.
  В карте приведений вашего ETL-скрипта, кстати, стоит тот же `Date` с тем же
  комментарием про 1970 — ограничение в контуре уже принято.

`CLICKHOUSE_SAFE_TYPES=0` возвращает родные типы ClickHouse: таблица будет «правильной»
с точки зрения ClickHouse и непригодной для конструктора.

Ограничения живут в двух константах `app/db/types.py`: `CH_SAFE_DDL` (чем заменяются
даты) и `CH_SAFE_DIGITS = 28` (бюджет разрядов). Если выяснится, что конструктор не
переваривает что-то ещё — `LowCardinality`, `Enum`, `Array`, `UInt64` — добавить это
туда дешевле всего; логика не изменится.

**Про диапазон дат.** ClickHouse держит `Date32` и `DateTime64` только в пределах
1900–2299 годов. Дата вне этого окна не вызывает ошибку: драйвер считает epoch,
упаковывает его в `Int64`, и сервер пишет **бессмысленное значение** — то есть
порча данных без единого сообщения. Поэтому адаптер ClickHouse перед вставкой
проверяет все колонки дат и времени и заменяет выходящие за диапазон значения на
`NULL`, а в конце вставки пишет в лог, сколько их было. Границы зависят от режима и типа:
1900–2299 для родных `Date32`/`DateTime64`, 1970–2149 для `Date` и 1970–2106 для
`DateTime`. Та же функция
(`types.fit_temporal`) помечает наивное время UTC и превращает `date` в `datetime`,
когда целевая колонка — `DateTime`.

**Про время — важное.** Оба типа времени уходят в ClickHouse как
`DateTime64(3, 'UTC')`, и наивные значения (PostgreSQL `timestamp`, то есть без
часового пояса) перед вставкой помечаются UTC. Если этого не сделать,
`clickhouse-connect` посчитает epoch через `datetime.timestamp()`, то есть
истолкует наивное время **в часовом поясе машины, где крутится Flask**, а
ClickHouse покажет его в поясе **сервера** — и вся копия окажется сдвинутой на
несколько часов, молча, без единой ошибки. Помечая UTC на записи и объявляя
колонку в UTC, мы сохраняем то, что видел человек в источнике: показания часов.
Значения со своим часовым поясом (`timestamptz`, `DateTime64(3, 'Europe/Moscow')`)
не трогаются — у них момент времени определён однозначно.

В ClickHouse все колонки создаются как `Nullable(...)`, а таблица — с
`ENGINE = MergeTree ORDER BY tuple()`. Причина конкретная: в ключе сортировки
`Nullable` использовать нельзя, а какая колонка годится в ключ — программа
знать не может. Пустой ключ снимает вопрос.

### 6.5. `app/db/postgres.py`

Четыре приёма, ради которых и выбран psycopg 3.

**Параметры словарём, а не строкой DSN.** Строка с `password=...` норовит
попасть в текст исключения, а оттуда — на экран.

**`sql.Identifier` для имён.** Это и есть настоящая защита от инъекции — не
регулярка на входе формы. Имя колонки, которое пользователь выбрал в списке, и
имя целевой таблицы, которое он ввёл руками, проходят через `Identifier`
всегда.

**Именованный курсор для чтения, с запасным вариантом.** `conn.cursor(name=...)`
создаёт курсор на стороне сервера: без имени psycopg втянет весь результат в
память, и на миллионе строк процесс умрёт. Но именованный курсор — это
`DECLARE ... CURSOR FOR <запрос>`, а в `DECLARE` можно положить не всё: скрипт
из нескольких операторов или `CALL` там не живут. Поэтому:

```python
try:
    cursor = conn.cursor(name=CURSOR_NAME)
    cursor.itersize = ITERSIZE
    cursor.execute(sql_text)
    columns = describe(cursor)
except psycopg.Error:
    cursor = self._fallback_cursor(conn, sql_text, ...)   # rollback + обычный курсор
    columns = describe(cursor)
```

Запасной путь закрывает неудавшийся курсор, откатывает прерванную транзакцию,
**включает `autocommit`**, берёт обычный курсор и прокручивает `nextset()` до
первого результата со строками. Три вещи про него надо знать:

- `autocommit` здесь не украшение. Без него psycopg держит открытую транзакцию,
  а PostgreSQL внутри транзакции запрещает целый класс операторов: процедура с
  `COMMIT` внутри падает с `invalid transaction termination`, `VACUUM` и
  `CREATE INDEX CONCURRENTLY` — с `cannot run inside a transaction block`. Раз
  мы согласились выполнять что угодно, пусть процедуры работают. Побочный
  эффект, который надо принять осознанно: записи, которые делает ваш запрос,
  теперь фиксируются, а не откатываются при закрытии соединения.
- этот путь **читает весь результат в память** процесса: обычный курсор psycopg
  забирает все строки до первой выданной. Это цена поддержки процедур; к ней
  прилагается `MAX_RU_DISTINCT_QTY`. Если источник — процедура на миллионы
  строк, выносите её результат во временную или обычную таблицу и выбирайте из
  неё `SELECT`: тогда работает именованный курсор и память не растёт.
- исключение перехватывается только вокруг `execute` и описания результата.
  Ошибка, случившаяся при чтении строк (сеть оборвалась на середине), в
  запасной путь не уходит — она превращается в `DbError`.

**Бесконечные и слишком большие даты читаются как `NULL`.** В PostgreSQL у
`date`, `timestamp` и `timestamptz` есть значения `infinity` и `-infinity`, а
также годы до 1 и после 9999 — в `datetime` Python такого нет, и psycopg честно
падает с `DataError: timestamp too small (before year 1): '-infinity'`. Для
инструмента, который копирует таблицу целиком, это означало смерть прогона из-за
одного значения в колонке, которую даже не переводят. Поэтому адаптер подменяет
загрузчики этих трёх типов на свои: они делают то же, что родные, но
непредставимое значение превращают в `NULL` и один раз на соединение пишут об этом
в лог.

```python
def lenient(native):
    class LenientLoader(Loader):
        format = native.format

        def __init__(self, oid, context=None):
            super().__init__(oid, context)
            self._native = native(oid, context)

        def load(self, data):
            try:
                return self._native.load(data)
            except psycopg.DataError:
                return None
```

Четыре детали, на которых это держится, и первая из них стоила отдельной ошибки.

**Нативный загрузчик вызывается внутри, а не наследуется.** Первая редакция делала
`class LenientLoader(native)` — и на машине с установленным `psycopg[binary]`
приложение падало с
`type 'psycopg_binary._psycopg.DateLoader' is not an acceptable base type`:
загрузчики C-расширения — это C-типы, от которых наследоваться нельзя. Создавать их
экземпляры при этом можно, поэтому класс наследуется от документированного
`psycopg.adapt.Loader`, а нативный держит внутри и вызывает его `load`. Побочная
выгода: разбор даты остаётся в C, подмена ничего не замедляет.

**Берётся тот загрузчик, который уже зарегистрирован в соединении**
(`conn.adapters.get_loader`), а не импортированный из `psycopg.types` — так работает
и с C-расширением, и без него, и не зависит от внутренних имён классов psycopg.

**Подменяются оба формата** (текстовый и двоичный) у каждого из трёх типов —
psycopg выбирает формат сам, и промахнуться здесь легко. Формат берётся у
нативного класса и ставится классу-обёртке, иначе регистрация уйдёт не в ту
таблицу.

**Регистрация идёт в соединение, а не в глобальный `psycopg.adapters`** —
приложение не меняет поведение psycopg в остальном процессе. Перед регистрацией
обёртка создаётся один раз «на пробу»: если на вашей сборке psycopg что-то пойдёт
не так, адаптер напишет в лог и оставит родной загрузчик, а не сломает запрос.

Цена решения, которую надо знать: `-infinity` в данных и `NULL` в данных станут в
копии одним и тем же. Если `-infinity` у вас значит «бессрочно», это надо
учитывать при чтении витрины.

**`COPY ... FROM STDIN` для записи, вместе с очисткой в одной транзакции.**
`executemany` на сотнях тысяч строк медленнее в разы. Генератор строк отдаётся
прямо в `copy.write_row`, то есть данные идут из источника в приёмник потоком,
не собираясь в список. При `clear=True` в той же транзакции сначала выполняется
`SET LOCAL lock_timeout = '10s'`, затем `TRUNCATE`. Таймаут блокировки — не
перестраховка: `TRUNCATE` требует исключительной блокировки, а соединение
источника в этот момент держит разделяемую блокировку на тех же таблицах. Если
указать целевой таблицей ту, из которой читает запрос, без таймаута запрос
повиснет навсегда (детектор взаимоблокировок эту ситуацию не видит — одна
сторона ждёт не блокировку, а приложение). С таймаутом через десять секунд
придёт понятная ошибка. **Целевой таблицей не стоит указывать таблицу,
участвующую в запросе источника.**

Описание результата строится так:

```python
for item in cursor.description:
    raw = type_name(item.type_code)          # OID → 'int4', 'text', ...
    columns.append(Column(name=item.name, kind=pg_kind(raw), raw_type=raw))
```

Существование таблицы проверяется через `to_regclass`, которому отдаётся уже
закавыченное имя:

```sql
SELECT a.attname, t.typname FROM pg_attribute a JOIN pg_type t ON t.oid = a.atttypid
WHERE a.attrelid = to_regclass(%s) AND a.attnum > 0 AND NOT a.attisdropped
ORDER BY a.attnum
```

`to_regclass` вернёт `NULL` для несуществующей таблицы — значит, строк не
будет, значит, `table_columns` вернёт `None`, значит, таблицу надо создать.
Так учитывается и `search_path`, и схема, если она указана. При создании
`схема.таблица` схема создаётся сама (`CREATE SCHEMA IF NOT EXISTS`).

### 6.6. `app/db/clickhouse.py`

Чтение — потоком блоков:

```python
context = client.query_row_block_stream(sql_text, settings=settings)
with context as blocks:
    columns = describe(context.source)
    yield Stream(blocks, columns)
```

Имена и типы колонок приходят в заголовке ответа, то есть доступны сразу после
входа в контекст и до чтения первого блока — на этом и держится метод
`columns()`, которому строки не нужны вовсе. Но «не нужны» не значит «не
приедут»: закрывая поток, драйвер **дочитывает и выбрасывает остаток ответа**
(`drain_conn`), иначе соединение нельзя вернуть в пул. На запросе вида
`SELECT * FROM events` по таблице в двести миллионов строк первая кнопка
перекачала бы всё это по сети, чтобы показать список колонок. Поэтому для
`columns()` запрос уходит с настройками

```python
PEEK_SETTINGS = {'max_result_rows': '1', 'result_overflow_mode': 'break'}
```

— сервер обрывает выдачу после первого блока. Текст запроса при этом не
меняется (обернуть его в `LIMIT 0` мы не можем, см. 6.3), ограничение целиком
на стороне сервера.

Запись — пачками по `INSERT_BATCH` строк через `client.insert(...)`:
драйвер сам узнаёт типы целевой таблицы и приводит к ним значения. Имена
колонок передаются явно, потому что порядок колонок в нашей таблице — это
порядок колонок результата, и совпадение с алфавитным порядком не гарантировано.

**База данных указывается только там, где она действительно нужна.** Клиент для
чтения создаётся с `database=...` (в запросе пользователя имена таблиц могут
быть без схемы), а клиент для метаданных, DDL и вставки — **без** него.
Причина не косметическая: `clickhouse-connect` отправляет базу параметром
каждого HTTP-запроса, а ClickHouse применяет её через `setCurrentDatabase` ещё
до разбора оператора. Если базы, которую вы указали в форме, пока нет, падает
даже запрос к `system.columns`, а `CREATE DATABASE IF NOT EXISTS` становится
недостижимым — его собственный запрос отвергают за упоминание этой базы. Без
параметра всё работает: имена в DDL и так полностью квалифицированы, а
`insert` получает базу отдельным аргументом.

Имена экранируются своей функцией, потому что `clickhouse-connect` аналога
`sql.Identifier` не предоставляет:

```python
def qi(name):
    return '`' + str(name).replace('\\', '\\\\').replace('`', '\\`') + '`'
```

Две детали, о которых легко не догадаться:

1. **HTTPS драйвер включает сам по порту** 8443 или 443 — отдельного флага в
   настройках подключения нет и не нужно. Если ваш ClickHouse за TLS на другом
   порту, это единственное место, где придётся дописать `secure=True`.
2. **Промах `LEFT JOIN` в ClickHouse даёт значение по умолчанию для типа, а не
   NULL.** Нас это прямо не касается (join'ов мы не делаем), но вспомните об
   этом, когда станете джойнить получившуюся таблицу: для `String` промах — это
   пустая строка, а не `NULL`, если не включить `join_use_nulls = 1`.

### 6.7. `app/db/__init__.py` — ленивая фабрика

```python
def get_adapter(params):
    if params.engine == 'postgres':
        from .postgres import PostgresAdapter
        return PostgresAdapter(params)
    if params.engine == 'clickhouse':
        from .clickhouse import ClickHouseAdapter
        return ClickHouseAdapter(params)
    raise DbError(f'неизвестный движок: {params.engine!r}')
```

Импорт драйвера — внутри ветки, а не на уровне модуля. Два следствия, оба
нужные: `app.db.base` и `app.db.types` импортируются там, где драйверов нет
вообще (тесты, раздел 13), и приложение работает с одним установленным
драйвером, если второй движок вам не нужен.

### 7.1. `core/prefilter.py` — надо ли переводить и что считать одним значением

```python
def needs_translation(value) -> bool:
    if not isinstance(value, str):
        return False

        return False
    return bool(CYRILLIC.search(value))


def normalize_key(value: str) -> str:

```

Самая высокооплачиваемая функция проекта — первая: она и ускоряет прогон в
разы, и убирает галлюцинации движка на нетекстовом входе. `ATOL-15`, `2024`,
пустая строка, `None`, число — в движок не уходят и в третьем блоке не
показываются вовсе. На записи они останутся как есть.

Эта же функция решает, какие колонки переводить, когда в первом блоке стоит
галочка **«Определить автоматически»**: программа идёт по всем колонкам
результата и оставляет те, в которых нашлось хоть одно значение с кириллицей.
Колонка с датами, числами или латиницей отпадает сама, и отдельной эвристики
«это текст?» не нужно.

Вторая функция важнее, чем кажется. «Ключ», «ключ » и «Ключ» с неразрывным
пробелом — это три разных значения для `SELECT DISTINCT` и одно и то же
значение для человека. Поэтому вводится **ключ**: нормализованная форма, по
которой значения группируются. Правило железное: **нормализуем ключ, а в
движок отправляем и в базу пишем оригинал.** Перепутать легко, и тогда модель
получит строку в нижнем регистре и потеряет признак, что слово в кавычках —
название.

Чем ключ расплачивается: `normalize_key` делает `casefold()`, значит «ОТГРУЗКА»
и «Отгрузка» — одно значение и один перевод. Для словаря значений это то, что
нужно; если вам важен регистр исходника, это единственное место, которое надо
менять.

### 7.2. `core/protect.py` — что внутри строки переводить нельзя

Самый окупаемый модуль после `prefilter`, и единственный, который работает без
всякой модели. Перед отправкой в движок из строки вырезаются термины из списка
«не переводить» и латиница; на их место ставятся метки; строка переводится; метки
заменяются обратно:

```
Труба по ГОСТ 12345  →  Труба по QQ1QQ 12345  →  Pipe per QQ1QQ 12345
                     →  Pipe per ГОСТ 12345
```

Защита нужна, но по умолчанию она **намеренно узкая**: из трёх прежних правил
осталось одно. Три ослабления сделаны по порядку, и каждое — ответ на то, что
значения оставались непереведёнными.

**Закавыченное больше не защищается.** Это главное изменение: `ООО "Ромашка"`
целиком уходит в движок, и `"Ромашка"` переводится. Раньше кавычки маскировались
«чтобы не получить `LLC "Chamomile"»`, но на реальных данных это означало, что
названия в кавычках не переводятся вообще, а значения, целиком состоящие из
закавыченного текста, не переводятся даже частично. Теперь приоритет обратный:
переводим всё, а точечные исключения задаются списком `keep` в глоссарии — там
им и место, потому что «какие названия не переводить» знает человек, а не
регулярка. Вернуть прежнее поведение можно одним флагом:
`Protector(..., quotes=True)`.

**Числа не маскируются.** Это второе ослабление. NMT-движок цифры
не переводит, а каждая маска — это риск: чем больше метод, тем вероятнее, что
движок одну из них проглотит или переставит. `Запчасти BOSCH 0 445 110 291`
раньше превращалось в строку с пятью метками и почти гарантированно
откатывалось; теперь это `Запчасти QQ1QQ 0 445 110 291` — одна метка. Включить
маскирование чисел обратно можно одним флагом: `Protector(..., numbers=True)`.

**Соседние защищённые куски склеиваются в одну метку.** Это третье ослабление.
Регулярка match'ит не один токен, а **серию** токенов вместе с разделителями
между ними, поэтому `Договор с Bill Inc` даёт одну метку на `Bill Inc`, а не
две. Чем меньше метод, тем меньше откатов.

**Проверка обратной подстановки.** Если после перевода хоть одна метка
потерялась, задвоилась или уехала за пределы списка, подстановка считается
неудачной. Метка ищется без учёта регистра: движок свободно превращает `QQ1QQ`
в `qq1qq`. Каждая метка должна встретиться **ровно один раз**: NMT умеет
дублировать короткие непонятные ему токены, и `Invoice QQ1QQ QQ1QQ` — это не
перевод, а брак.

**Неудачная подстановка больше не означает «без перевода».** И самое важное: такое значение отправляется в движок **второй раз, без
защиты вообще**, и ответ берётся как есть (в статистике это столбец «без
защиты»). Да, в этом случае закавыченное название может оказаться переведённым
— зато в таблице не останется русского текста, а человек всё равно смотрит
третий блок и может вернуть название руками. Если и второй заход вернул пустоту,
значение откатывается на оригинал («откат на оригинал»).

**Строка, в которой после маскирования не осталось кириллицы, в движок не
идёт.** `ГОСТ 12345` при `keep ГОСТ` целиком состоит из защищённых частей —
переводить там нечего, и значение возвращается как есть. В статистике это
«защищено целиком»: если число большое, значит `keep` или глоссарий закрывают
слишком много.

Чего в защите сознательно **нет**: правила на кириллические артикулы вида
`[А-ЯЁ]{2,}\s*\d+` (`ТО-2`, `ГОСТ 12345`). Такое правило было в вашей ветке
`main`, и для номенклатуры оно полезно — но оно же съедает `НДС 20` и `ИНН 7701`,
то есть ровно те строки, которые переводить надо. Если в ваших данных артикулов
много, добавьте этот шаблон в `Protector._build` и посмотрите на столбец
«защищено целиком» до и после.

### 7.3. `core/glossary.py` — три механизма, а не один словарь

Важно понять сразу: это **не один словарь, а три механизма в трёх точках
пайплайна**, и попытка уместить их в один `dict` — главная причина, по которой
глоссарий кажется бессмысленным.

| раздел | когда работает | что делает |
|---|---|---|
| `[whole]` | вместо движка | значение целиком равно известному коду: `ООО = LLC` |
| `[before]` | до движка | заменить русскую подстроку принятой английской: `руб. = RUB` |
| `[after]` | после движка | движок выбрал синоним вместо принятого термина: `bill = invoice` |
| `[keep]` | до движка, внутри `protect` | не переводить эту подстроку никогда: `ГОСТ` |

Формат — INI-файл, а не `dict` в коде: править терминологию не повод делать
коммит в `.py`. Файл перечитывается на каждый прогон, перезапуск приложения не
нужен.

```ini
[whole]
ООО = LLC
КПП = IEC

[before]
Общество с ограниченной ответственностью = LLC
руб. = RUB

[after]
bill = invoice

[keep]
ГОСТ
```

**Варианты регистра писать не нужно.** `whole` ищется по нормализованному ключу
(`casefold`, `ё → е`, сжатые пробелы), а правила `term` компилируются с
`IGNORECASE`, поэтому `ООО`, `ооо`, `Ооо` и `ООО ` — это одна строка глоссария.
Нужны только разные **формы** термина: сокращение и полное название, потому что
это разные строки текста, а не разный регистр.

**Длинные варианты применяются раньше коротких** — правила сортируются по длине
источника при загрузке, независимо от порядка строк в файле. Поэтому
`Товарно-транспортная накладная` не превратится в `consignment note транспортная`
из-за правила `Накладная`, а `НДС не облагается` сработает раньше, чем `НДС`.

**Почему INI, а не TSV.** Первая редакция файла была с разделителем-табом, и это
оказалось ошибкой: таб невидим, а правило с пробелом вместо него парсер молча
выбрасывал. На живом файле так умерли семь добавленных правил
(`СФР`, `ФОМС`, `ЦОД`, `СХД`, `Работает`, `Выключено`, `Проект №`) — человек их
дописал, приложение их не увидело, ошибки никто не показал. В INI разделитель
видно глазом, лишние пробелы вокруг `=` не значат ничего, вид правила задан
разделом один раз на группу, а не повторяется в каждой строке. И главное —
**молчаливых потерь больше нет**: любая невнятная строка теперь останавливает
прогон с конкретным текстом.

| что сделано не так | что покажет приложение |
|---|---|
| `АО` без `= перевод` | `[whole] «АО» — нет перевода после знака =` |
| `[whoel]` вместо `[whole]` | `раздел [whoel] не распознан, бывают только …` |
| правило выше первого раздела | `строка 1: правило должно лежать внутри раздела — …` |

Две детали про направление. У `[whole]` и `[before]` слева **русское**, у
`[after]` — **английское** (слово из ответа движка). Латиница, которая получилась
после `[before]`, дальше автоматически попадает под защиту (7.2), поэтому движок
её не испортит. В `[keep]` строки идут без `=` вообще. Замена подставляется
буквально: обратная косая черта и `\1` справа — это символы, а не ссылки на
группы регулярки.

**Знаки на концах источника учитываются.** Границы слова подставляются только с
тех сторон, где источник начинается или заканчивается буквой или цифрой. Поэтому
`Проект №` срабатывает и в `Проект № 5`, и в `Проект №5`, а `ГОСТ` не затронет
`ГОСТы`. На TSV-варианте правило `Проект №` не работало вовсе — это была вторая
тихая поломка.

`whole` сам по себе закрывает только значения-коды: на `Договор поставки
оборудования` точное совпадение не сработает никогда, а это основная масса
данных. Поэтому нужны все три механизма.

И главное про глоссарий: **он результат работы системы, а не вход** — и
единственное место, где перевод закрепляется навсегда. Накопительного кэша в
проекте нет (7.5), поэтому порядок работы такой: прогнали, посмотрели третий
блок, увидели, что движок переводит `счёт` как `bill`, а у вас принято `invoice`
— дописали строку в `glossary.ini`. Файл перечитывается на каждый прогон, так что
следующий запуск уже учтёт правку, и она останется в репозитории, а не в
служебной базе на сервере.

В репозитории файл уже заполнен: организационно-правовые формы (аббревиатуры **и
полные названия** — `ООО` и `Общество с ограниченной ответственностью`),
категории персонала и объекты (`ПЕД.РАБ`, `УВП`, `ППС`, `Корпус`, `Общежитие`),
реквизиты и регистры (`ИНН`, `КПП = IEC`, `ОГРН`, `ОКВЭД`, `ЕГРЮЛ`), налоги,
взносы и фонды (`НДС`, `УСН`, `ЕСХН`, `СФР`, `НДС не облагается`), инфраструктуру
и состояния (`ЦОД = DC`, `СХД = DSS`, `Работает = Running`), типовые документы
(`Акт сверки`, `Товарно-транспортная накладная`, `Счёт-фактура`, `УПД`), единицы и
пометки (`руб.`, `коп.`, `шт.`, `в т.ч.`, `Итого`). Разделы `[after]` и `[keep]`
оставлены пустыми с примерами в комментариях. Это основа, а не истина — правьте
под свою терминологию.

Понятия «домен» (разные наборы терминов для юридических и финансовых колонок) в
реализации нет. В форме его негде выбрать, а угадывать по данным — отдельная
задача; один глоссарий на инсталляцию честнее, чем три, из которых применяется
случайный.

### 7.4. `core/translate_client.py` — клиент LibreTranslate

```python
payload = {'q': chunk, 'source': 'ru', 'target': 'en', 'format': 'text'}
```

Четыре обязательные детали:

- **`q` — массив.** LibreTranslate поддерживает батчи, и это главное, что
  спасает от «запрос на каждую строку».
- **`source: 'ru'` строго, никогда `auto`.** Автоопределение языка на коротких
  метках ошибается и переводит с неверного языка молча, без ошибки.
- **Проверка длины ответа.** Если движок вернул меньше элементов, чем приняли,
  дальше всё поедет со сдвигом: перевод чужого значения встанет к чужому
  ключу. Падать надо здесь, а не через три таблицы. Ответ в виде одной строки
  (так LibreTranslate отвечает на `q` из одного элемента) обрабатывается
  отдельно.
- **Любая сетевая ошибка — это `TranslationError` с понятным текстом**, а не
  трейсбек `requests` на экране.

#### Батчи по символам, а не по штукам

`TRANSLATION_TIMEOUT` — это таймаут **одного запроса**, а не всего прогона.
Прогон из пяти тысяч значений законно идёт четверть часа; беда начинается,
когда в один запрос попадает столько текста, что движок не успевает ответить за
таймаут. А NMT-движок тратит время не на количество строк, а на количество
**токенов**: двадцать четыре метки по двадцать символов он переведёт за секунды,
двадцать четыре абзаца по семьсот — за минуты. Поэтому батч ограничен с двух
сторон: `TRANSLATION_BATCH` строк **и** `TRANSLATION_CHARS` символов, что
наступит раньше. Значение длиннее лимита уезжает в запрос в одиночку.

#### Что происходит при таймауте

Раньше таймаут одного запроса убивал весь прогон: пользователь видел
`Read timed out`, а полтора десятка минут работы уходили в никуда. Теперь
`requests.Timeout` — это отдельное исключение `TranslationTimeout`, и клиент на
него реагирует сам:

```
батч не уложился в таймаут
   ├─ дождаться, пока движок освободится (GET /languages, не дольше таймаута)
   ├─ разделить батч пополам и попробовать каждую половину
   └─ одно значение всё равно не уложилось → вернуть None
```

Две детали, без которых это не работает. **Ожидание обязательно**: после
таймаута клиент бросает соединение, но движок **продолжает считать** брошенный
батч, и повторный запрос встанет в очередь за ним — поэтому сначала дешёвый
`GET /languages`, который вернётся только когда движок освободится. И
**`None` вместо исключения**: значение, которое не переводится ни за какие
деньги, не должно валить прогон — пайплайн оставляет для него оригинал и считает
его в статистике отдельной строкой «не уложилось в таймаут». В третьем блоке оно
видно сразу: единственное русское среди английских.

Клиент пишет в лог приложения строку на каждый батч — сколько значений, сколько
символов, сколько секунд, — поэтому долгий прогон перестал быть чёрным ящиком, а
«какие значения тормозят» видно без догадок (`scripts/bench_translate.py`,
раздел 13).

Интерфейс из одного метода `translate(texts) -> list[str | None]` делает движок
сменным: другой движок — новый класс с тем же методом, остальной код не
меняется.

### 7.5. `core/pipeline.py` — сценарий целиком

Три функции, вызываемые откуда угодно: из Flask, из консольного скрипта, из
теста.

```python
collect(adapter, sql_text, columns, limit) -> ({колонка: {ключ: оригинал}}, rows)
translate(values_by_column, glossary, protector, translator, rows) -> Translated
apply(source_adapter, target_adapter, sql_text, pairs_by_column, table, batch) -> Applied
```

**`collect`** читает результат запроса потоком **один раз на все колонки** и
складывает первое встреченное написание каждого ключа отдельно по каждой
колонке. Пустой список колонок означает «определить автоматически»: берутся все
колонки результата, а те, где не нашлось ни одного значения с кириллицей,
отбрасываются. Значения без кириллицы, `None` и пустые пропускаются
(`prefilter`). Предел `limit` считается **суммарно по всем колонкам**: когда
уникальных значений становится больше, работа прекращается с внятным текстом, а
не с убитым процессом.

**`translate`** сначала **сливает значения всех колонок в один набор ключей**:
одинаковое значение в двух колонках — это один запрос к движку и один перевод,
иначе консистентности не будет. Потом раскладывает значения по источникам
правды. Порядок важен:

```
1. глоссарий, вид whole        → берём из глоссария, движок не трогаем
2. остальное                   → очередь в движок
3. очередь: glossary.term (ru) → protect.mask → движок батчами
                               → glossary.term (en) → protect.unmask
4. у кого подстановка не сошлась → второй заход в движок без защиты
5. у кого движок вернул None     → оригинал, «не уложилось в таймаут» (7.4)
6. пары раскладываются обратно по колонкам (вкладки третьего блока)
```

Обратите внимание на порядок в пункте 3: пост-правка терминов применяется к
ответу движка, **пока метки ещё на месте**. Если сделать наоборот, правило
`term bill invoice` переименует контрагента `Bill Inc`, которого защита как раз
и прикрывала, — и никто этого не заметит.

**Памяти между прогонами нет.** Накопительного кэша переводов в SQLite в проекте
не осталось — он убран сознательно (раздел 11). Следствие принимаем прямо: каждое
нажатие «Выполнить перевод» отправляет в движок всё, что не закрыл глоссарий, а
правки, сделанные руками в третьем блоке, живут до нажатия «Применить» и дальше
существуют только в целевой таблице. Если перевод нужно закрепить — его место в
`glossary.ini`: это теперь единственная долговременная память проекта, и она
читается при каждом прогоне, без перезапуска приложения.

Глоссарий стоит выше движка, потому что это решение человека, записанное
заранее. На значениях-кодах (`ООО`, `ИНН`, `НДС`) он закрывает перевод целиком и
бесплатно, на длинных строках подставляет принятые термины до движка — см. 7.3.

**`apply`** — то, что происходит после нажатия «Применить», и самая
ответственная функция проекта.

```
1. из присланных пар собрать по карте на каждую колонку:
   normalize_key(оригинал) → перевод
   (пустой перевод = «оставить оригинал», такие пары в карту не попадают)
2. заново выполнить запрос пользователя, взять колонки результата
3. колонки целевой таблицы = колонки результата, переведённые приведены к text
4. подготовить целевую таблицу (см. ниже)
5. прогнать строки потоком: в каждой переведённой колонке заменить значение по
   её карте, остальные колонки отдать как есть, замены посчитать
```

Замена идёт по ключу, а не по точному совпадению строки, и это важно: в данных
`Договор`, `договор ` и `Договор` с неразрывным пробелом — три разных строки,
в третьем блоке они показаны одной, и перевод обязан встать во все три. Чего в
карте нет — остаётся оригиналом; в частности, значения, появившиеся в данных
между двумя прогонами запроса.

**Про счётчик замен.** `apply` возвращает не только число записанных строк, но и
число фактически заменённых значений, и оно показывается в сообщении. Если там
ноль, значит карта переводов ни к одной строке не подошла — например, пары
собраны для одной колонки, а запрос с тех пор поменялся. Копия при этом
записана, но осталась русской, и программа говорит об этом прямо, а не
рапортует об успехе.

Приведение `as_text` применяется ко всем колонкам, чей логический тип —
`text`: это и есть то место, где массив ClickHouse становится строкой
`["а", "б"]`, а не ломает вставку. Та же функция используется в `collect`,
и это обязательно: ключ значения должен считаться от одной и той же строки на
обоих шагах, иначе перевод не найдёт своё значение при записи.

Правила подготовки целевой таблицы (`prepare_target`) — ровно три, и их надо
знать до первого запуска:

| состояние таблицы | что делает программа |
|---|---|
| нет | создаёт по колонкам результата, пишет |
| есть, имена и порядок колонок совпадают | **очищает и пишет заново** |
| есть, колонки другие | отказывается и показывает оба списка колонок |

Второе правило означает, что **повторный прогон перезаписывает таблицу
целиком**, а не добавляет строки. Так результат идемпотентен: поправили
переводы, нажали «Применить» ещё раз — получили ровно то же, что и с первого
раза, но с правками. Цена: если указать имя существующей таблицы, у которой
случайно такие же имена колонок, её содержимое будет заменено. Отдельной
галочки «перезаписать» в интерфейсе нет сознательно — это внутренний
инструмент на три кнопки; осторожность здесь на стороне того, кто вводит имя.
Третье правило — та самая защита от опечатки в имени: таблица с другой
структурой не трогается вообще.

Очистка выполняется не отдельным шагом, а внутри записи (`insert(...,
clear=True)`), и в PostgreSQL это **одна транзакция**: `TRUNCATE` и `COPY`
коммитятся вместе, поэтому неудачная запись не оставляет вас без прошлых данных.
В ClickHouse транзакций нет, и там это честно два шага: если вставка упадёт
после `TRUNCATE`, таблица останется пустой, а ошибка будет на экране — повторите
«Применить». Сравнение с существующей таблицей идёт **только по именам и порядку
колонок**: совпадение имён при несовместимых типах выяснится ошибкой вставки, и
в ClickHouse к этому моменту таблица уже будет очищена.

Перед созданием и сравнением список колонок проходит через `fit_columns`
приёмника (6.2) — для PostgreSQL это обрезка имён до 63 байт, чтобы повторный
прогон не упирался в «колонки другие».

Память переводов пополняется **после** успешной записи: если запись не
удалась, подтверждёнными правки не считаются.

Статистика прогона (`Stats`) возвращается наружу и показывается в строке
сообщений: сколько строк просмотрено, какие колонки взяты, сколько значений к
переводу, сколько закрыто движком, вторым заходом без защиты, глоссарием,
сколько защищено целиком и сколько откатилось на оригинал. Это и есть индикатор,
работает ли слой `core`: если велик «откат на оригинал» — ваши данные ломают
метки, и стоит посмотреть на `Protector`; если велико «защищено целиком» —
защита съедает слишком много, см. 7.2; если появилось «не уложилось в таймаут» —
движку не хватает `TRANSLATION_TIMEOUT` на отдельных значениях, см. 7.4. Нулевые
счётчики в сообщение не попадают, поэтому строка короткая, пока всё хорошо.

## 8. Слой `routes` и `forms`: три блока одной формой

### 8.1. Одна форма, четыре кнопки

```
┌─ 1. База с переводимыми значениями ─────────────────────┐
│ СУБД  хост  порт  пользователь  пароль  база            │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ SELECT ... (запрос, вызов функции, скрипт)          │ │
│ └─────────────────────────────────────────────────────┘ │
│               Колонки:  ┌──────────────────┐            │
│ [Выполнить]             │ id · int4        │  [x] Опре- │
│                         │ kind · text   ◄──┤  делить    │
│                         │ note · text   ◄──┤  автома-   │
│                         └──────────────────┘  тически   │
└─────────────────────────────────────────────────────────┘
┌─ 2. База для переведённых значений ─────────────────────┐
│ СУБД  хост  порт  пользователь  пароль  база            │
│ Целевая таблица: [ public.contracts_en ]                │
│ [Выполнить перевод]                                     │
└─────────────────────────────────────────────────────────┘
┌─ 3. Значение и перевод ─────────────────────────────────┐
│ ┌ kind (42) ┐ note (7)                                  │
│ ├───────────┴─────────────────────────────────────────┐ │
│ │ Договор поставки    │ [Supply contract            ] │ │
│ │ ООО "Ромашка"       │ [LLC "Ромашка"              ] │ │
│ └─────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────┘
                                            [Применить]
```

Ключевое решение: **все три блока лежат внутри одного `<form>`**, а кнопок
несколько. При нажатии любой из них на сервер уходят все поля сразу — и
реквизиты источника, и реквизиты приёмника, и правки переводов. Серверу нечего
запоминать между шагами, и это то, что позволило выбросить реестр подключений
(раздел 5).

Какая кнопка нажата, WTForms сообщает сам: `SubmitField` приходит в данных
только та, которой нажали, поэтому в обработчике достаточно проверить
`form.run_query.data`.

Следствие, которое надо принять: **валидаторы `DataRequired` на полях не
годятся.** При нажатии «Выполнить» поля второго блока ещё пусты, и форма с
`DataRequired` не прошла бы валидацию целиком. Поэтому все поля
необязательные, а нужное для конкретного действия проверяется в обработчике:

| кнопка | что обязательно заполнить |
|---|---|
| Выполнить | реквизиты источника и запрос |
| Выполнить перевод | то же плюс выбранные колонки **или** галочка «Определить автоматически» |
| Применить | то же плюс реквизиты приёмника и целевая таблица |

Обратите внимание: «Выполнить перевод» **не требует** реквизитов приёмника.
Перевод к приёмнику отношения не имеет, и заставлять заполнять второй блок
ради того, чтобы посмотреть, что получится, незачем.

### 8.2. Список колонок: скрытое поле и `validate_choice=False`

Поле выбора колонок — `SelectMultipleField`: переводить одну колонку в таблице
на двадцать колонок смысла мало, а размечать их по одной за прогон — тем более.
Рядом галочка `src_auto` «Определить автоматически»: когда она стоит, выбор в
списке **игнорируется** и колонки определяет `prefilter` (7.1). Это не замена
выбору руками, а другой режим: автоматика берёт всё, где есть кириллица, и на
широком результате может набрать больше значений, чем разрешает
`MAX_RU_DISTINCT_QTY` — тогда программа скажет об этом, и колонки надо будет
отметить руками.

Колонки результата известны в момент отрисовки — они получены из описания уже
выполненного запроса, поэтому `SelectMultipleField` здесь уместен. Одна
тонкость: список уезжает в браузер и возвращается следующим запросом, а
`choices` к моменту валидации надо восстановить. Делается это скрытым полем, в
котором список лежит строками `имя<TAB>тип`:

```python
form.src_columns.data = '\n'.join(f'{c.name}\t{c.raw_type}' for c in columns)
form.src_column.choices = [(c.name, f'{c.name} · {c.raw_type}') for c in columns]
form.src_column.data = [name for name in (form.src_column.data or []) if name in names]
```

Третья строка нужна, чтобы отметки не слетали при повторном нажатии
«Выполнить»: выбранное приходит из браузера и остаётся выбранным, если такая
колонка есть и в новом результате.

Тип в подписи — не украшение: по нему видно, что `kind · text` переводить
осмысленно, а `qty · int4` нет. Выбрать можно любую колонку: если в ней нет
кириллицы, `prefilter` отсеет всё, и вкладки для неё не будет — это понятнее,
чем спрятанная из списка колонка.

`validate_choice=False` у поля обязателен: проверять значение по списку,
который сам пришёл из браузера, смысла нет, а имя колонки всё равно уйдёт в
`sql.Identifier` и сверится с описанием результата (`column_index` упадёт с
внятным текстом, если такой колонки в результате нет).

### 8.3. Пары «значение — перевод» и вкладки без JavaScript

Каждая строка третьего блока отдаёт три поля:

```html
<td>{{ pair.source }}
    <input type="hidden" name="column" value="{{ column }}">
    <input type="hidden" name="source" value="{{ pair.source }}"></td>
<td><input type="text" name="translation" value="{{ pair.translation }}"></td>
```

Пары собираются из `request.form.getlist`, а не через WTForms: их количество
заранее неизвестно, и `FieldList` здесь только добавил бы конструкций. Три
списка приходят параллельно и сшиваются `zip_longest` — порядок полей в теле
POST совпадает с порядком в документе, поэтому соответствие сохраняется, даже
если часть переводов очищена. `column` в каждой строке и есть то, что позволяет
применять несколько колонок за один раз: обработчику не нужно помнить, какие
вкладки он рисовал, — вся раскладка приехала вместе с правками.

Автоэкранирование Jinja закрывает вопрос с кавычками и угловыми скобками в
данных: значение с `"` или `<script>` внутри приедет обратно ровно таким, каким
было.

**Вкладки сделаны на CSS, без единой строки JavaScript.** Приём старый и
надёжный: на каждую колонку — скрытая радиокнопка, сразу за ней `<label>` с
`for`, сразу за ним панель. Переключение — это `:checked` у соседа:

```css
.tabs { display: flex; flex-wrap: wrap; }
.tab-label { order: 1; }
.tab-pane { order: 2; width: 100%; display: none; }
.tab-radio:checked + .tab-label + .tab-pane { display: block; }
```

`order` нужен, чтобы все ярлыки встали в строку над панелями, хотя в разметке
они перемешаны — иначе селектор соседа не сработает. Правил на каждую вкладку не
требуется, поэтому колонок может быть сколько угодно.

Две важные детали. Поля в скрытых панелях **всё равно отправляются**:
`display: none` на отправку формы не влияет, поэтому «Применить» видит правки
со всех вкладок, а не только с открытой. И сама радиокнопка уезжает на сервер
как `tab=<колонка>` — обработчик возвращает её в ответ, чтобы после нажатия
кнопки открытой осталась та же вкладка.

**Высота третьего блока фиксирована.** Таблица пар лежит внутри
`<div class="pairs-scroll">` с `max-height: var(--pairs-height)` и
`overflow-y: auto`, поэтому страница не растёт от числа значений: сколько бы их
ни было, блок занимает те же ~420 пикселей и прокручивается внутри себя. Высота
задана одной переменной в начале `styles.css` — поменять её можно в одном месте:

```css
:root { --pairs-height: 420px; }
```

Заголовок таблицы при прокрутке остаётся на месте (`position: sticky`), а его
нижняя граница нарисована через `box-shadow`, а не `border`: при
`border-collapse: collapse` граница у «липкой» ячейки не рисуется — это известная
особенность, на которую легко потратить вечер.

### 8.4. `app/routes.py`

Один обработчик, одна точка выхода:

```python
form = TranslationForm()
form.src_column.choices = stored_columns(form)
pairs = posted_pairs()

if form.validate_on_submit():
    try:
        if form.run_query.data: ...
        elif form.run_translate.data: ...
        elif form.apply_result.data: ...
    except Exception as error:
        current_app.logger.exception('действие не выполнено')
        notice = str(error)
        notice_kind = 'error'
```

**Почему перехват такой широкий.** Этому инструменту нужен настоящий текст
ошибки: «колонки `kind` нет в результате», «relation "contracts_en" does not
exist», «движок перевода недоступен». Сообщения драйверов, `DbError`,
`PipelineError` и `TranslationError` — всё это человеку полезно и ни в одном из
них нет пароля (реквизиты передаются словарём, а не строкой DSN, см. 6.5).
Полный трейсбек уходит в лог приложения, на экран — одна строка.

**Про валидацию.** Форма проверяет только форму: заполнено, не слишком длинно.
Что колонка существует и что запрос корректен, форма знать не может — это
выясняется при выполнении запроса. Настоящая защита от инъекции при этом не в
форме и не в регулярках, а в `sql.Identifier` и `qi()` внутри адаптеров.

Объекты `core` создаются на каждый запрос: `Cache` — это открытие файла SQLite,
`load_glossary` — чтение небольшого INI, `Protector` — компиляция регулярки.
Всё вместе — доли миллисекунды, а взамен глоссарий правится без перезапуска
приложения.

```
              │            │  движок ──────┼─► LibreTranslate     │
              │◄─ страница ┤  пары в блок 3│                      │
              │  с перевод.│               │                      │
поправил      │            │               │                      │
руками,       │            │               │                      │
нажал         ├─ POST / ──►│ apply         │                      │
«Применить»   │            │  rows ────────├─► запрос целиком      │
              │            │  prepare ─────┼──────────────────────┼─► CREATE TABLE
              │            │  insert ──────┼── поток строк ──────►│   TRUNCATE + COPY
              │            │               │                      │   (одна транзакция)
              │◄─ «Записано│               │                      │
              │   строк: N»│               │                      │
```

Обратите внимание на три вещи. Реквизиты обеих баз уходят на сервер в каждом из
трёх запросов и нигде между ними не хранятся. Запрос к источнику выполняется
дважды. На третьем шаге оба соединения открыты одновременно: строки идут из
источника в приёмник потоком, не собираясь в памяти целиком.

## 10. Безопасность: что надо знать про эту конструкцию

Четыре вещи, каждая — следствие принятых решений, а не недосмотр.

**Приложение выполняет произвольный SQL от имени пользователя, без режима
только чтение.** Это назначение первого блока и прямое требование к
реализации (6.3). Права — не приложения, а того, чьи реквизиты введены, поэтому
разграничение доступа работает само собой: заводите для этой работы учётку с
нужными правами и не давайте в форму суперпользователя. И помните про запасной
путь PostgreSQL (6.5): он работает с `autocommit`, то есть побочные записи
вашего запроса фиксируются, а не откатываются.

**Пароли в HTML страницы.** Следствие отказа от серверного хранения реквизитов
(раздел 5). Смягчается `Cache-Control: no-store` и HTTPS; полностью убирается
только возвратом к серверному хранению.

**Приложение подключается к любому адресу, который введут, и авторизации у
самого приложения нет.** Это внутренний инструмент. Если он станет доступен
шире вашей команды, понадобится и авторизация, и белый список хостов.

**CSRF-токен не истекает по времени** (`WTF_CSRF_TIME_LIMIT = None`). Это не
забывчивость: третий блок человек правит руками и может просидеть над ним час.
С дефолтным часовым лимитом «Применить» после долгой правки молча не сработало
бы. Токен остаётся привязанным к сессии браузера; если форма всё же не прошла
валидацию, причина показывается в строке сообщений, а не проглатывается.

## 11. Чего здесь нет и почему

- **Режима «только чтение»** — убран по требованию: источником данных бывает
  хранимая процедура, которой нужно создавать временные таблицы (6.3).
- **Ограничения «один оператор за раз»** — по той же причине.
- **Celery, Redis, RQ, фоновых потоков, слоя `jobs`** — пока хватает
  синхронного обработчика с ограничением по объёму (раздел 12).
- **JavaScript** — ни строчки, и это решение. Единственный список, который
  нужен (колонки результата), приходит вместе с перерисованной страницей.
  Что мы получили: нет `/api/*` ручек, то есть нет второго места, где надо
  аккуратно обращаться с реквизитами; нет рассинхронизации между DOM и
  сервером; состояние страницы — это сама форма, и его целиком держит браузер.
  Что потеряли: каждое действие перезагружает страницу. Для внутреннего
  инструмента на три кнопки это приемлемо.
- **SQLAlchemy и любого ORM** — здесь пишется DDL и bulk-SQL, ORM только
  мешает. Рефлекс «Flask → Flask-SQLAlchemy» подавить.
- **Авторизации** — внутренний инструмент (раздел 10).
- **Реестра подключений** — не нужен без фоновых заданий (раздел 5).
- **Таблицы-словаря из двух колонок** — результат прогона это английская копия
  результата запроса.
- **Накопительной памяти переводов (SQLite)** — была, убрана по требованию вместе
  с модулем `core/cache.py`, полем `reviewed` и каталогом `instance/`. Цена
  понятная и её надо знать: переводы между прогонами не запоминаются, каждый
  прогон заново спрашивает движок, а ручные правки после «Применить» живут только
  в целевой таблице. Закрепить перевод теперь можно одним способом — строкой в
  `glossary.ini` (7.3), и это честнее: терминология лежит в репозитории, а не в
  служебном файле на сервере.
- **Защиты закавыченного текста** — кавычки переводятся наравне с остальным
  (7.2); что не переводить, перечисляется в `keep`.
- **Доменов глоссария** — один глоссарий на инсталляцию (7.3).
- **Разбивки длинных текстов по предложениям** — если в колонке абзацы, а не
  метки, NMT-движку нужна разбивка. Отдельная задача, не сейчас.
- **Перевода имён колонок** — в целевой таблице имена колонок остаются
  исходными. «Таблица на английском» означает английские **значения**
  переведённых колонок; структура исходника сохраняется целиком, включая
  названия колонок и их порядок.
- **JavaScript для вкладок** — третий блок с вкладками сделан на CSS (8.3).

## 12. Когда синхронного обработчика перестанет хватать

Перевод десяти тысяч значений — это минуты, а HTTP-запрос столько не живёт:
gunicorn по умолчанию рвёт соединение через 30 секунд, браузер — раньше.

Сейчас этого нет, и держится это на одном предположении: **`MAX_RU_DISTINCT_QTY`
ограничивает объём так, что перевод успевает за время запроса.** Пока
уникальных значений единицы тысяч, а не сотни тысяч, синхронного обработчика
достаточно, и он экономит вам реестр заданий, поток, опрос прогресса,
JavaScript и отмену.

Признак, что предположение перестало быть верным, однозначный: таймаут вместо
третьего блока. Тогда понадобится `app/jobs/registry.py` — словарь заданий,
`threading.Thread`, прогресс и отмена, плюс опрос из браузера на одну ручку.
Менять при этом придётся только обработчик: `pipeline.translate` ничего не
знает о том, кто его вызвал, и принять `progress`/`cancelled` ему ничего не
мешает. Первым делом поднимите `--timeout` у gunicorn — часто этого хватает.

Второй предел — размер самой страницы. Высота третьего блока фиксирована, и
вкладки показывают по одной колонке за раз, так что **визуально** страница не
растёт никогда. Но в документе живут все поля всех вкладок: столько, сколько
уникальных значений во всех выбранных колонках вместе. Тысячи — нормально,
десятки тысяч — уже тяжело браузеру. Поэтому `MAX_RU_DISTINCT_QTY` считается
суммарно, а не по колонке.

### Замер скорости движка

Когда прогон идёт долго или движок перестаёт укладываться в таймаут, нужно знать
**какие именно значения** его тормозят. Для этого `scripts/bench_translate.py`:
он берёт файл со значениями — по одному на строку, — прогоняет их через ту же
подготовку, что и приложение (глоссарий + маскирование), переводит **по одному** с
замером времени и показывает самые медленные, пропускную способность в символах в
секунду и оценку времени на тысячу значений:

```bash
export LIBRE_TRANSLATE_URL=http://127.0.0.1:5000
clickhouse-client --query "select distinct kind from t format TabSeparatedRaw" > values.txt
python3 scripts/bench_translate.py --file values.txt --limit 60
```

Флаг `--tsv` нужен, если строки файла имеют вид `колонка<TAB>значение<TAB>перевод`:
тогда берётся вторая колонка.

```
  0.08 с     29 симв.  Договор поставки оборудования
  1.78 с    708 симв.  Очень длинное наименование целевой статьи расходов...
итого по одному: 1.9 с на 4 значений
пропускная способность: 395 символов/с
батч из 4 значений (767 символов): 1.9 с
оценка на 1000 значений такого размера: 8.0 мин
[!] батч съедает больше половины таймаута (3 с) — уменьшайте TRANSLATION_CHARS
```

Если пропускная способность низкая на всех значениях — дело в движке (один поток,
CPU, конкуренция с приложением за ядро); если медленные только единицы значений —
это длинные тексты, и лечится это `TRANSLATION_CHARS`, а не таймаутом.

### Приведение типов в уже существующих таблицах

Переводчик теперь создаёт правильные таблицы, но те, что созданы раньше (и вообще любые
таблицы, собранные не планировщиком), остаются с типами, от которых конструктор зависает.
Для них `scripts/retype_clickhouse.py`: он обходит все колонки всех таблиц базы, считает
для каждой целевой тип **той же функцией, что и переводчик** (`app/db/types`), и
приводит их через `ALTER TABLE ... MODIFY COLUMN`. Трогает он ровно то же, что
ограничено в 6.4 — `Date32`, `DateTime64` и широкий `Decimal`; `Int64`, `UUID`, `Bool`,
`LowCardinality`, `Enum`, `Array` не задевает.

```bash
export CH_PASSWORD=...
# разбор без изменений — что и куда поедет
python3 scripts/retype_clickhouse.py --host 10.38.47.22 --database dwh2_bi_uni

# применить
python3 scripts/retype_clickhouse.py --host 10.38.47.22 --database dwh2_bi_uni --apply
```

```
база dwh2_bi_uni: таблиц и представлений 3, к переводу колонок 1, вручную 1

--- можно привести автоматически ---
  kadry_en.сумма: Decimal(32, 4) -> Decimal(24, 4)

--- нужно руками ---
  kadry_en.дата_рождения: Nullable(Date32) -> Nullable(Date)   3 значений не влезут в новый тип
```

**По умолчанию он ничего не меняет** — только показывает разбор и выходит с кодом 1,
если осталось что-то, требующее решения. Четыре случая он сознательно не трогает:

- **значения не влезут в новый тип.** Перед каждым сужающим приведением скрипт считает
  запросом, сколько значений выходит за новые границы (даты вне 1970–2149 для `Date` и
  1970–2106 для `DateTime`, числа крупнее новой целой части). Если такие есть — колонка уходит в «вручную», потому что `ALTER` в
  ClickHouse не падает, а **молча подрезает** значение до границы. `--force` выполняет
  приведение всё равно, `--no-check` отключает проверку (быстрее, но слепо).
- **колонка в ключе сортировки** — `ALTER` её запрещён; нужна пересборка таблицы
  (создать рядом, `insert select`, `exchange tables`).
- **тип не приводится напрямую** — `Array(Date32)`, `Map(..., Date32)` и прочие
  составные: для них нужно решать, что значит «та же колонка, но с другим типом внутри».
- **представления** — у них тип колонки определяется запросом, а не DDL. Скрипт печатает
  готовый `create or replace view` с нужными `cast`, но **не выполняет его**: подменять
  определение представления вслепую нельзя.

`--table` ограничивает работу одной таблицей (можно повторять), `mutations_sync = 2`
заставляет скрипт дождаться реального завершения мутации, а не вернуться сразу.

Ещё одна вещь, о которой надо знать: `prepare_target` сравнивает только **имена** колонок
(7.5). Поэтому уже существующая переведённая таблица со старыми типами при повторном
«Применить» будет перезаписана **в своих старых типах**. Чтобы она стала правильной, её
надо либо удалить и создать заново переводом, либо прогнать этим скриптом.

### Тесты

Тесты **не лежат в каталоге приложения** — это отдельная папка рядом с проектом,
так в репозиторий и в поставку не попадает ничего, кроме самой программы:

```
/home/amsterdam/
├── data-translator/         ← приложение, то самое, что в git
└── data-translator-tests/   ← тесты, в git не входят
    ├── fakes.py
    ├── test_core.py
    ├── test_postgres.py
    ├── test_translate_client.py
    └── test_web.py
```

```bash
cd ../data-translator-tests
python3 -m unittest discover -s . -t .

# если каталог проекта лежит не рядом или назван иначе
DT_PROJECT=/путь/к/data-translator python3 -m unittest discover -s . -t .
```

Путь к приложению тесты берут из `DT_PROJECT`, а по умолчанию ищут каталог
`data-translator` рядом с собой.

Тесты делятся на четыре части, и все запускаются одной командой.

**`test_core.py` — без всего.** Ни Flask, ни драйверов БД, ни сети, ни сервера:
только стандартная библиотека. Покрыты `prefilter`, `protect` (что кавычки уходят
в движок, что `quotes=True` возвращает защиту, склейка латиницы в одну метку,
откат при потерянных и задвоенных метках, второй заход без защиты), `glossary`
(все четыре раздела, порядок «длинные раньше коротких», границы слова у источников
со знаком на конце, буквальная замена с обратной косой чертой и три вида ошибок
формата), `db/types` (разбор типов обеих СУБД, обрезка имён,
точность decimal, пометка наивного времени UTC, обнуление дат вне диапазона
ClickHouse, ограничения для ClickHouse целиком — что отличается от родных типов ровно
в датах и `Decimal`, бюджет 28 разрядов на десятке комбинаций, распознавание типов,
которые трогать не надо, цели приведения, приводимость, идемпотентность — отказ при
повторяющихся именах колонок) и весь `pipeline` на поддельном адаптере — несколько колонок за прогон,
один запрос к движку на значение, встречающееся в двух колонках, создание и
перезапись целевой таблицы, отказ при несовпадении колонок, замена значений по
ключу, согласованность ключа между сбором и записью, приведение к тексту, учёт
статистики.

**`test_translate_client.py` — клиент движка.** Требует только `requests`.
Проверяет нарезку батчей по штукам и по символам (включая значение, которое
длиннее бюджета и уезжает одно), и главное — поведение при таймауте на поддельной
сессии: что батч делится пополам до тех пор, пока не уложится, что порядок ответов
сохраняется после всех делений, что одно неподъёмное значение возвращает `None`, а
не валит прогон, и что отказ в соединении таймаутом не считается и не
переспрашивается.

**`test_postgres.py` — подмена загрузчиков даты.** Требует только `psycopg`
(без него пропускается). Проверяет на поддельном загрузчике, что обычное значение
проходит насквозь, `infinity`/`-infinity` и неразбираемое значение становятся
`NULL`, формат берётся у нативного класса, класс кэшируется и его модуль не
выглядит как `psycopg.types` — иначе psycopg подменил бы его своей C-версией и
подмена молча перестала бы работать. Два теста закрывают уже случившиеся грабли:
что нативный загрузчик **не оказался базовым классом** и что подмена работает над
типом, который наследование запрещает (ровно как C-типы из `psycopg_binary`).
Ещё два — что неработающий или отсутствующий нативный загрузчик просто
пропускается, а не валит подключение.

**`test_web.py` — весь путь по трём кнопкам.** Требует только Flask (без
него эти тесты сами себя пропускают, остальные идут как обычно). Приложение
поднимается тест-клиентом с поддельным адаптером БД и поддельным движком
перевода, и проверяется именно то, что руками проверять дольше всего: CSRF-токен
туда и обратно, список колонок, уехавший в скрытое поле и вернувшийся оттуда,
множественный выбор и режим «Определить автоматически», вкладки третьего блока
(сколько, какая открыта, какие строки в каждой), распознавание нажатой кнопки,
перерисовка пароля, экранирование значений с кавычками и тегами, сообщения об
ошибках (пустые поля, нечисловой порт, просроченная форма, ошибка СУБД,
превышенный предел значений, пары для несуществующей колонки), заголовок
`Cache-Control`, двукратное выполнение запроса, фиксированная высота третьего
блока, перевод закавыченных значений — и главное: **что в целевую таблицу уходит
именно та правка, которую человек внёс руками в третьем блоке**, по всем колонкам
сразу.

Адаптеры БД тестами не покрыты сознательно: проверять их надо не заглушкой, а
живым сервером.
